## Protocol

| ID | Decision | Reason |
| --- | --- | --- |
| P-01 | Protocol is exactly as briefed (UUIDs, 15-byte layout, flags, Device Info JSON). Unchanged. | Fixed contract; both sides must match. |
| P-02 | Power field is always sent (the Architecture called it optional). ## Engine (M4, M5)

| ID | Decision | Reason |
| --- | --- | --- |
| E-01 | Energy per interval = (P_prev + P_cur) x dt in microwatt-milliseconds (= nJ), kept **doubled** so no halves; per-minute accumulators are exact integers well under 2^53; closed minutes fold into a BigInt, so the session total is exact for any length. | Architecture sections 8 and 14. Arch D4 accepted as proposed. |
| E-02 | "Recorded time" includes bridged time (bridged is the part spanning lost packets). Average power = energy / recorded time. | Architecture section 12 data-quality line shows both; this makes the relationship explicit. |
| E-03 | Restart vs late vs lost packet rules are in `sequence.ts` (documented at the top): duplicate = same seq; late = seq at most 32 behind AND time back by about the same number of sample periods (a wider window would swallow a device that rebooted after a few seconds); device time backwards, or seq far backwards, = restart. Limit: a reboot heard again only after a longer uptime than before looks like lost packets (the gap is over 1 s, so nothing is invented). | Architecture left the heuristics open. Arch D7 accepted. |
| E-04 | The gap record for a device restart is attached to the session that ends; its end is the arrival time of the new session's first packet. | The old session is the one with a hole at its end. |
| E-05 | Gap cause: sensor-fault > hint from the source (link down, then stale) > lost packets if seq jumped > stale. A sensor-fault interval is excluded in full and labelled `stale` (link open, no valid measurement) since `GapRecord.cause` has no sensor value. | Only four causes in the seam. |
| E-06 | Samples with the sensor-fault flag carry no measurement: not integrated, not charted, last real V/I kept, alert raised. | Never invent data. |
| E-07 | Step detector details: strict comparisons at half (a sample exactly at half stays in its state); pulse window = first sample above half to first sample below half, energy includes the falling interval and excludes the rising one; step time = pulse start; min gap measured start-to-start; a merged pulse emits nothing. | Architecture section 8 left these open. |
| E-08 | Cadence uses step END times in the last 10 s of session time x 6; null until 10 s of continuous recorded time exist (resets on any excluded gap or fault). | PRD M10 / Architecture section 8. |
| E-09 | Measured sample rate = samples in (window start, now] over elapsed device time, windows of at least 1 s; windows over 2 s (outages) are not trusted. Low-rate warning below 19.5 Hz (0.5 Hz slack for window jitter). | PRD: warn below 20. |
| E-10 | Totals (M6, M13, M15) add earlier **real-device** sessions only; the worker passes 0 for demo and replay so demos never pollute ESG numbers. After a restart, the closed session's energy and steps move into the all-time total. | PRD: demo must never be mistaken for real generation. |
| E-11 | The sensor-limit alert stays up for 3 s after the last clipped sample; the instantaneous flag in `metrics.sensorLimitReached` has no hold. | Avoid flicker. |
| E-12 | `Pipeline` never reads a clock: arrival time and "now" are inputs. All engine tests are deterministic. | Testability. |

## Storage (M7)

| ID | Decision | Reason |
| --- | --- | --- |
| ST-01 | Raw samples are stored as packed 15-byte chunks of about one second (key session + start time). A chunk grows while open and is final once the next one starts. Per-sample arrival time is not stored: a sample's time is the chunk start plus the device-time difference. | Arch D5. Integration and clocks use device time, so arrival time adds nothing, and 15 bytes per sample is the documented size. |
| ST-02 | Reprocessing feeds the stored samples through a fresh `Pipeline`, anchoring the first sample at the session start; steps, minute buckets and totals are replaced, raw samples and gap records are never touched. Verified: totals identical to live (energy, steps, recorded, bridged, excluded, peak, step events). | PRD/Architecture: reprocessing equals live. Gap causes (link down, stale) come from live hints that are not in the raw log, so they are kept as recorded rather than re-derived. |
| ST-03 | Schema v1 plus an additive v2 (`meta` store). Dexie 4 opens a database that a newer app already upgraded; `openDatabase` reports `newerThanApp`. A test checks that every version only adds. | Arch section 16: additive migrations, tolerate one version newer. Dexie 4 already tolerates it, so no custom fallback is needed. |
| ST-04 | History ranges over one hour come from minute buckets (average power; voltage and current are NaN); one hour or less from raw samples at full resolution. | Architecture section 9. |
| ST-05 | One transaction per flush. On failure the batch is kept and retried, `lastError` is set (alert `storage_error`), and streaming continues in memory. | Architecture section 12. |
| ST-06 | **Retention is implemented and tested (`applyRetention(days)`, default policy 30 days) but nothing calls it automatically.** | Architecture says to offer a CSV export first; deleting raw data silently would break that. It needs a Settings decision from you and the frontend (then an `applyRetention` call can be added to the seam). The quota check (warn at 80%) and the persistent-storage request ARE wired. |
| ST-07 | `importSessionJson` is implemented in the store and on the worker but not on `DashboardEngine`; `startReplay(file)` covers viewing a backup. | Keeps the seam small. |

## Worker and facade (M7, M8)

| ID | Decision | Reason |
| --- | --- | --- |
| W-01 | The worker handles lifecycle messages (start, stop, a link that closes the session, delete-all, failure) strictly in order; packets are handled synchronously when none is in flight and wait in a queue otherwise. History queries run concurrently. | Found by the facade tests: `start` is asynchronous, and packets sent right after it landed in the previous pipeline and a throwaway session. Fixed and covered. |

| W-04 | `createMockEngine()` runs the real worker host on the main thread (no Web Worker), against its own IndexedDB `force-mock`; `connect()` starts the simulator. | Lets the frontend build every state with no hardware and without touching real data. |

## Firmware (M3, M9)

| ID | Decision | Reason |
| --- | --- | --- |
| F-01 | The INA219 is read by direct registers, not the Adafruit library: configuration word 0x399F (32 V, gain /8, 12-bit, no averaging, continuous) written and read back; current mA = shunt register x 10 uV / shunt milliohm; bus voltage = register >> 3 x 4 mV. | Brief allows either; no calibration register means no library rounding, and the maths is host-testable. |
| F-02 | `SENSOR_LIMIT_MA = 320000 / INA219_SHUNT_MOHM` (3200 mA at 0.1 ohm). The limit flag is set when the current reaches it or the ADC saturates. | One constant to change when the shunt is confirmed. |
| F-03 | Device time is read from `esp_timer_get_time()/1000` right after the scheduled wake-up, before the I2C transaction. | "At the moment of the reading"; the reading takes about 1 ms. |
| F-04 | If the INA219 stops answering: packets continue with the fault flag and zero readings; a separate low-priority task retries init every second. The sampler owns the I2C bus while the sensor is OK, the retry task only while it is not (never both). | Brief: keep sending, retry in the background, never block. |
| F-05 | The 128-bit service UUID is in the advertising data and the name in the scan response (together they exceed 31 bytes). Browsers merge both for the `FORCE-` + service filter. | BLE advertising size limit. |
| F-06 | Sampler to BLE task through a static FreeRTOS queue (64 packets). A full queue drops the newest packet; a refused notify drops and moves on; both are counted and logged, and the sequence gap shows the loss. | Brief: never block, no heap in the loop. |
| F-07 | Pinned: `espressif32@6.13.0` (Arduino core 2.x), `NimBLE-Arduino@2.3.9`, PlatformIO Core 6.2.0 in CI. `SAMPLE_RATE_HZ` may be 1..100 and must divide 1000. | Reproducible builds. |
| F-08 | Connection interval (15-30 ms), latency 0, 4 s timeout are requested after connect on a best-effort basis; the central may choose differently. | Smooth 20-100 notifications per second. |
